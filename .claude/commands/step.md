---
description: Build one step of the Placard plan. Usage: /step 5
argument-hint: <step number, e.g. 5>
effort: medium
---
Build step $ARGUMENTS of Placard. The person types only `/step $ARGUMENTS`; everything you need is in this command, `CLAUDE.md`, `build-plan/mcp.md` and the step file. Follow this routine in order.

**1. Find the step and check the plan.** First check the folder: `build-plan/` and `screens/` must be directly in the folder you're in (the `placard` repo root; from step 1 on, `package.json` too). If they aren't, tell the person to open the `placard` folder in VS Code and stop. Next check that the plan is the plan's own version. In step 0, check that the starter is complete: `CLAUDE.md`, `MEMORY.md`, `.claude/settings.json`, `build-plan/spec.md`, `build-plan/mcp.md`, the 4 files in `build-plan/ui/`, the 22 in `build-plan/steps/` (`00` to `20` and `hostinger.md`), the 5 in `build-plan/swarm/`, `screens/index.html`, and the 60 photos in `public/library/`. If any is missing, tell the person to unzip `placard-starter.zip` again and stop. From step 1 on, step 0's commit holds the plan exactly as it was unzipped, so compare with it: take its hash from `git log --reverse --format=%h --grep='^step 0: project setup' | head -1`, then run `git diff --name-only <hash> -- build-plan screens public/library CLAUDE.md .claude/commands .claude/settings.json` (changed or deleted plan files, committed or not) and `git ls-files --others --exclude-standard -- build-plan screens public/library` (added files). Both must print nothing. If either lists a file, show the list to the person and ask whether to put the plan's version back; on yes, run `git checkout <hash> -- <the changed files>`, delete the added ones, and check again. Never write or fix a plan file any other way. Then open the file in `build-plan/steps/` whose number is $ARGUMENTS (`5` and `05` both mean `05-*.md`). If $ARGUMENTS is `hostinger`, use `build-plan/steps/hostinger.md` (it has the same seven sections; its order check is "Step 15 committed").

**2. Check the model.** Every step is built on Opus 5.5 (`claude-opus-5-5`) at medium effort. If you are Opus 5.5, carry on. If you are Sonnet 5.5 (`claude-sonnet-5-5`) and the **Model** row in the step's header table says "Sonnet 5.5 is enough", carry on. Otherwise tell the person: "This step runs on Opus 5.5 at medium effort. Pick it in the model button (or type `/model claude-opus-5-5`), then type `/step $ARGUMENTS` again." and stop.

**3. Read.** Read `CLAUDE.md` and `MEMORY.md` if they aren't already in your context (Claude Code loads both at the start of every conversation), then `build-plan/mcp.md`, the whole step file, and every file in its section "2. Read first".

**4. Check the order.** Unless this is step 0, run `git log --oneline` and look for the commit message of the previous step (from that step's section "6. Commit"). Step 16 and `hostinger` are optional, so the step before 17 is 15. If it's missing, say which step to run first and stop. If this step's own commit is already there, say the step is done and stop.

**5. You do first.** If section "1. You do first" lists tasks, show them to the person exactly as written and ask them to reply "done" when finished. Wait. If the section says "Nothing", go straight on.

**6. Connect and verify.** Skip the MCP part in step 0 (it creates the servers). For every server in the step header's **MCP** row: call `init` on `next-devtools`; for the others make one harmless read (for example, list projects, teams, branches or users). If any server needs a sign-in, give the person the steps in `build-plan/mcp.md` §3, naming the account, team or project to pick, wait for "done" and check again. Don't start building with a server missing. Then verify the "You do first" tasks without printing any secret: the `.env.local` keys they name are filled in (`grep -c '^NAME=.' .env.local`), from step 1 on the `dev` branch answers (`select 1` through `neon`), the dev server starts, and what they set up in a service looks right through that service's MCP server (for example, the sign-in methods in Clerk, the project in Vercel, the variable *names* in Vercel). If something is missing, say exactly what and wait again.

**7. Build.** Do every item in section "3. Build", in the order written. Items that name an MCP server are done through that server, following `build-plan/mcp.md` §4; items that change `neon.ts` end with the `npx neon deploy` the item names (`CLAUDE.md` › "Neon"). After each item that adds or changes a route, read the dev server's errors through `next-devtools` and fix them. Build nothing else. If an item is unclear or conflicts with the spec, the design system or the reference screens, stop and ask.

**8. Responsive.** Apply section "4. Responsive" and design-system §13. Start the app, then run `node scripts/check-responsive.mjs` on the "Pages to check" in the step's header table (`--signed-in` for app pages, `--site <id>` for site pages; this script exists from step 1 on). Compare its screenshots in `notes/responsive/` with `screens/screenshots/` at 390, 768 and 1440 (and 1024 for editor screens). Fix every failure and every visible difference in layout, spacing, type or colour, then run it again until it passes.

**9. Code checks.** `npm run typecheck`, `npm run lint`, `npm run build`, and `npm test` once tests exist; with the dev server running, `next-devtools` reports no errors; from step 1 on, `npm run db:check` passes and `npx drizzle-kit generate` says there are no schema changes (if it wrote a migration, the schema changed without one: delete that file and make the named migration the step asks for). Fix what fails.

**10. Check it works.** Go through section "5. Check it works" item by item, except items marked **(prod)** (they run in part 13). Do each check yourself where you can: `playwright` for anything in the browser, `posthog` for events, persons, flags and replays, `clerk` for users and settings, `neon` for SQL on `dev`. For checks that need the person (signing in with Google, paying with a test card, editing DNS at a registrar, a real phone), ask them to do it and tell you what they saw. Report every item as pass or fail, with links: the saved PostHog insight (`Check · …`) behind every number, person pages, session recordings with timestamps, the Clerk dashboard page, the Vercel deployment or log, and the SQL you ran with its result and the Neon Console link of the branch.

**11. Review.** Run the CodeRabbit review on this step's changes. Fix findings that are real bugs or break `CLAUDE.md`; list the ones you skipped and why.

**12. Commit (and ship).** First add the step's memory block (section "7. Memory") to the end of `MEMORY.md`, word for word, once (skip it if its heading is already there), ending it with a `- Not in the plan:` line if the step did something its plan didn't describe (`CLAUDE.md` › "Memory"). Then commit everything with the exact message in section "6. Commit". If the step has **(prod)** items, push to `main` (`git push`; the person approves it), then follow the deployment of that commit with `vercel` until it is Ready. If the build fails, read its build log through `vercel`, fix the cause, commit as `step N: fix <what>`, push and follow the new deployment. Steps without **(prod)** items aren't pushed, except step 0, which adds `origin` and pushes as its section "6. Commit" says.

**13. Production checks.** If the step has **(prod)** items, run them now against `https://APP_DOMAIN` with `vercel`, `neon` (`select` on `main`), `posthog`, `clerk` and `playwright`, and read the runtime errors since the deploy through `vercel` (there should be none). If one fails, fix it, add a `- Not in the plan:` line about the fix to the step's block in `MEMORY.md`, commit both as `step N: fix <what>`, push, follow the deployment and check again.

**14. Finish.** Reply with: what was built (3–5 lines), the checklist with pass/fail and links, what you did through each MCP server and the Neon CLI (one line each), anything you couldn't do or had to decide, and the last line `Next: type /clear, then /step N (Opus 5.5, medium)` with the next step's number, adding `; Sonnet 5.5 is enough` when that step's Model row says so (for example `Next: type /clear, then /step 6 (Opus 5.5, medium; Sonnet 5.5 is enough)`). After step 15 the last line is `Next: type /clear, then /step 17 (Opus 5.5, medium). Optional any time from now: /step 16 (custom domains) and /step hostinger (the Hostinger move)`. After step 20: `Next: the app is built and rehearsed. Optional, if you haven't made them: /step 16 (custom domains) and /step hostinger (the Hostinger move)`. After step 16 or `hostinger`, check `git log`: name the first of steps 17–20 that isn't committed, in the usual form; if all four are, name the other optional one if it isn't done; otherwise "All steps done." Then stop. Don't start the next step.
